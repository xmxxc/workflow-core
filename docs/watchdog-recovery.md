# watchdog 通知循环与安全恢复

同一 attempt 的宿主错误与最大轮次超时分别去重。去重记录与消息在同一 SQLite 写事务提交，按 dispatch、round、attempt、故障类型及宿主 turn/错误指纹保存；进程重启不会清空记录。新 turn、错误内容变化、新 round/attempt 可以生成新通知。旧版本 `host_error` 表保留兼容，升级后每个当前故障可能再通知一次；升级不修改旧消息或其确认状态。回滚旧版本会重新暴露循环，因此应先停止 relay。

## 已有消息积压的恢复

以下步骤由操作者针对已核实的 state 目录和 scope 显式执行。不要把事故队列整体重新送入模型。

1. 先用只读 `wfc status` 核对 waiter 的 PID、进程启动身份、命令行、scope、state 目录和 controller owner。停止该范围唯一的 relay；Unix 可对核对后的 PID 发送 SIGTERM。确认对应进程已经结束且消息计数稳定。PID 本身不能作为身份凭据，不要停止其他 scope 的 relay。
2. 保留原始数据库、relay 日志、宿主会话、工作目录及报告。在线 SQLite 使用 backup API 复制一致快照，避免只复制一个可能有 WAL 的 `router.db`。证据可能含敏感信息，应限制访问。不要删除现场、worker 或旧候选。
3. 从报告与工作目录核对候选 commit、未提交修改、round/attempt、验证结果和独立审查结论。#17 的原候选和 r2 报告需要保留；已有报告不等于最终复核通过。
4. 基于已核实证据编写精简交接：事故原因、候选身份、已完成工作、未决问题、当前 owner/attempt、待审报告和所需下一步。由新的 controller 会话读取交接；默认使用新的 state/scope，保留旧队列供审计。不要在事故范围自动启动旧 relay。
5. 对需要继续使用原范围的情形，先离线盘点每条消息的 ID、body hash、状态和外部接收证据。`unknown` 仍表示发送结果不确定，不能直接重放。只有证据确认已送达时，才使用 `wfc resolve <id> --actor ... --reason ... --evidence ... --body-hash ...` 记录对账；这不表示业务已处理。`wfc ack <id>` 表示业务已处理，只能在实际处理后使用。
6. 批量确认、清理或归档均需单独、显式执行并保留操作清单与依据。本修复不自动确认、清理或重新投递任何积压消息。确认候选通过审查后，再由操作者决定是否恢复旧范围和启动唯一 relay。

本次受控测试使用临时 state 和受控 tmux/宿主，不接触事故现场，也不把受控验证标记为真实宿主验收。
