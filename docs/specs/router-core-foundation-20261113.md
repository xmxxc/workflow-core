# workflow-core 核心可靠性与平台基础规格

状态：已确认，待按依赖实施。日期：2026-11-13。

## Problem Statement

workflow-core 当前能把一个任务派给一个宿主会话，worker 通过 `done` 或 `ask` 唤醒总控，核心路径已经可用。但总控在角色完成、提问、宿主异常、进程无效、消息投递不确定或账号切换时，还需要人工检查屏幕、SQLite 和工作树才能判断下一步。平台实现也直接依赖 Unix/Tmux，无法自然扩展到原生 Windows。

用户要一个小而完整的 router：总控派发任务和角色，角色完成或需要处理时唤醒总控，突发情况有明确状态和恢复入口。业务流程、审查规则、模型选择、工厂界面和发布决策由上层调用方（当前是 super-coding）负责。

## Solution

为 workflow-core 建立稳定的任务、轮次、执行尝试、消息、唤醒和运行后端接口。核心持久化每次执行的身份、归属、输入和结果状态，能在重复回报、投递超时、总控切换、worker 异常和 router 重启后继续对账。核心观察“进程在线、宿主活动、等待人类、未知结果”等状态，提供显式中断、接替和回收语义。

执行后端只负责启动、观察、输入、中断、恢复和关闭运行单元。具体实现可为 tmux、Herdr 或结构化宿主协议；选择后端不改变核心消息和任务语义。平台层负责文件锁、进程身份、路径、命令行和后台生命周期，使核心可以在 Unix 和原生 Windows 上运行。Windows 的完整支持以真实闭环验收为准。

## User Stories

1. 作为总控，我想给一个明确角色派发一个任务，使 worker 能收到唯一的任务身份和回报位置。
2. 作为总控，我想给同一 worker 派发下一轮任务，使修复或复核可以关联到前一轮而不会覆盖历史结果。
3. 作为 worker，我想报告完成、提问、阻塞或失败，使总控能被唤醒并区分这些情况。
4. 作为总控，我想知道消息是未发送、发送结果未知、已接收还是已处理，使我能安全决定是否重放。
5. 作为总控，我想在接手一个范围时取得唯一控制权，使旧总控不能继续消费或派发同一范围。
6. 作为总控，我想重复提交同一个请求而不会重复启动同一运行单元，使网络超时和进程崩溃可以安全恢复。
7. 作为总控，我想区分 worker 进程还活着、宿主有活动、等待人类、宿主报错和结果未知，使突发情况不会被误判成完成或自动重做。
8. 作为总控，我想中断或关闭一个运行单元并得到明确结果，使取消、未送达和未知状态不会混为一谈。
9. 作为总控，我想把未完成任务交给另一个宿主，同时保留原任务、改动和旧运行归属，使接替不会产生两个 writer。
10. 作为调用方，我想读取机器可解析的状态和事件，建立不同的工作流外壳、通知器或控制台，而不用读取屏幕文本。
11. 作为 Unix 用户，我想继续使用适合本机的执行后端，而不用迁移既有任务或改变上层调用语义。
12. 作为 Windows 用户，我想在没有 WSL 的环境中运行核心命令、启动受支持宿主并完成一次派发到回收的闭环。
13. 作为维护者，我想用受控替身测试重复、崩溃、超时、迟到回报和取消竞态，而不用依赖真实模型额度。
14. 作为维护者，我想知道某项跨平台能力是否已经真实验证，使文档不会把源码存在误写成平台支持。

## Implementation Decisions

- 核心术语固定为：scope（一个总控范围）、dispatch（一个角色任务）、round（同一 dispatch 的一次任务轮次）、attempt（一次实际运行尝试）、message（总控与 worker 之间的持久消息）、wake（把消息交给总控的机制）、backend（运行单元的启动/观察/输入/中断/关闭实现）、handoff（旧 attempt 到新 attempt 的接替关系）。
- 核心接口不包含 issue、PR、review、模型策略、角色选择规则或业务授权；这些属于上层。核心必须识别并记录通用宿主故障（额度/认证/策略拒绝、进程退出、权限提示、输入未送达、协议断开、超时），给出机器可读的故障类别和原始诊断。上层决定是否换角色、换模型、暂停或人工处理。
- 每个 dispatch 保存 scope、角色、任务输入摘要、工作目录、报告/结果引用、backend 身份、当前 round/attempt 及状态。历史 round/attempt 不被覆盖。
- 消息和运行回执使用稳定 request/message ID、结果摘要和状态版本。重复的相同回执返回既有结果；相同 ID 的不同内容返回冲突。发送结果未知时保持可查询，不做无条件重试。
- controller ownership 使用可变代数或等价的单一所有者凭据。旧所有者在消费消息、发送输入或提交结果时被拒绝并得到可诊断状态。
- 状态至少区分 queued、running、waiting-human、blocked、unknown、completed、failed、cancelled、reclaimed。`unknown` 表示事实不足，不表示失败或可安全重做。
- backend 接口包含 create、inspect、read、submit、interrupt、resume、close；每个操作返回 definitely-not-sent、accepted、uncertain、completed、refused 等机器可读结果。终端接受不等于 worker 完成。
- 先定义接口，再把当前执行机制接到第一个 backend；不要求 tmux 永久保留，也不要求第一版马上实现多个 backend。已有数据库和 CLI 兼容性由每张票明确维护。
- 平台薄层处理文件锁、进程 creation identity、后台 detach、命令 argv、UTF-8/路径和配置权限。Windows 不能复用 Unix `fcntl`、`ps`、`os.kill(pid, 0)` 或 shell quoting 假设。
- Windows 第一候选是 Herdr backend；Paseo/Codeg 协议服务是后续候选。只有完成真实 Windows 闭环后，才能在文档中标为支持。
- 核心仍优先使用 Python 标准库和 SQLite；不把完整 IDE、daemon、DAG、审查工厂或第三方 runtime 复制进单文件 router。

## Testing Decisions

- 最高测试 seam 是 router 的命令行和持久状态接口；真实宿主由受控替身模拟输入接受、延迟、失败、退出、重复回报和迟到事件。
- 测试只断言外部行为：消息状态、唤醒内容、状态转移、重复请求结果、所有者隔离、恢复和清理结果；不把 SQLite 表布局或内部函数作为契约。
- 保留现有 `tests/test_router.py` 的 fake CLI/tmux 方式，新增可替换 backend contract tests，使同一套场景可以跑替身和未来 backend。
- 每个 ticket 至少覆盖：正常路径、重复/崩溃路径、一个权限或输入失败路径；跨平台 ticket 另加 Windows 原生命令行和路径样本。
- 可靠性测试覆盖 router 在写消息、发送、ACK、完成回报和关闭之间退出的窗口；重启后只能得到可对账状态，不能声称外部副作用 exactly-once。
- Windows 最终验收必须在原生 Windows 主机完成，不用 WSL/SSH 代替；覆盖一宿主派发、提问/唤醒、完成、异常、恢复、接替和回收。

## Out of Scope

- super-coding 的 issue 扫描、角色表、独立审查、候选放行、GitHub 操作、合并、部署和 live-verify。
- LobeHub、Orca、Paseo、Codeg、Tern 或 Pachat 的完整 UI、DAG、通知平台、账户系统或服务端复制。
- 默认模型选择、配额购买、自动换模型和业务层重试策略。
- 自动批准权限、自动执行生产破坏性动作和绕过宿主安全提示。
- 在没有真实 Windows 闭环证据前发布“原生 Windows 已支持”。

## Further Notes

9 张票按依赖顺序发布。前 5 张建立可靠任务/唤醒/突发恢复；第 6、7 张抽象和移植执行基础；第 8、9 张验证 Herdr 与原生 Windows。每张票都应保持单一可演示路径，失败时留下可继续的状态。

本规格的核心完成标准是：总控能派发一个角色，worker 能完成或提问并唤醒总控，异常能进入可诊断和可接替状态，router 重启后仍能对账。具体外壳可在此之上自行决定怎样使用这些能力。
