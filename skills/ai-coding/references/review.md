# 独立审查

## 三级审查

- **首次完整审查**：覆盖 PR 基线 O 到候选 A 的全部净变化，包括新增、删除、重命名的文件，以及测试、配置、资源和文档。
- **增量复核**：修复到 B 后，审 A 到 B 的补丁及其关联的调用、契约和行为，写明复用了哪些旧结论；影响或证据不清时扩大范围。
- **最终完整审查**：放行前审 O 到最终候选 F 的全部净变化，修复补丁作为最终 PR 的一部分一起审。补丁逐个通过或旧结论拼接都不能代替它。首次完整审查之后候选、基线、需求和标准都没变时，首次审查可兼作最终审查，在账本里记录这一双重用途。

每次审查绑定候选身份 `repo + PR + target + base + merge-base + head + tree`。增量起点已不是当前候选的祖先时（rebase、force-push），先核对真实差异和旧证据是否仍适用；无法可靠界定时，回到完整审查。审查范围完整，不等于每轮都重跑全部测试，验证等级按 [验证分层与测试矩阵](verification.md) 选择。

## 独立性

独立审查者没有参与该候选的设计落地、实现或修复；作者自己做的检查记作作者自查。独立的证据是：

- 审查者的任务或会话标识与所有作者都不同，并已记录；
- 审查者只读固定快照或独立工作树，看不到作者的对话和未提交内容。

会话名、模型名、窗口标题都不算证据。各派发模式接受哪种独立上下文，见对应的 dispatch 文件。修复后的复核可以由未参与实施的原审查者继续做。

## 审查任务字段

```markdown
# <票据> · 独立<首次完整/增量/最终完整>审查 · 第<N>轮

固定候选：<repo + PR + target + base + merge-base + head + tree>
范围：<base..head，或上次获审候选..head 加关联影响>
快照：<只读快照或独立工作树的绝对路径>
需求与标准：<Issue/规格、项目规则、历史发现及其归属（本票/继承/后续）>
验证：<等级/矩阵、触发依据、可复用的固定证据>
授权：只读审查；可以 <在 PR 发 COMMENT 审查记录>；停在报告写完
留痕：PR 上发布下方的审查记录（必须）；无法发布时，把正文写进报告并标“待发布”
回报：<reports/ 绝对路径>
```

用项目已有的审查工作流取得同一快照的 Standards / Spec 双轴结论；总控不再另起一组重复的双轴审查。发现阻塞时，保留失败证据和正常对照，修复交还 worker。

## PR 审查记录

```markdown
## 独立<审查/复核>记录 · 第<N>轮
审查者：<任务/会话标识>，未参与本候选实施/修复；作者：<标识>
阶段：<首次完整/增量/最终完整>；候选：<候选身份>；范围：<起点..head>
增量时：<上次获审候选、补丁范围、旧结论覆盖边界>

### Standards
<保留审查工作流的本轴报告与发现数>

### Spec
<保留审查工作流的本轴报告与发现数>

发现：<严重度、归属、触发、实际验证、处置>
复用：<未变范围>；限制：<工具/平台/未执行项>
结论：<本固定范围通过/有阻塞>；下一步：<修复/增量复核/最终审查/可放行>
```

## 复核请求

当总控或用户认为某个发现不适用、严重度偏高或前提不成立时：

1. 总控写 `prompts/<票据>-review-r<N>-reply.md`，列出要复核的发现、反证和需要审查者回答的问题，交给原审查者；原审查者不可用时，交给另一位独立审查者。
2. 审查者写补充报告 `reports/<票据>-review-r<N>-addendum.md`，原报告保持不变。结论只能是以下三种之一：维持；降级；对已核实路径不适用，并附条件。
3. 补充结论按上面的审查记录格式发到 PR。

## 处置决定

用户对发现做出的决定，由总控发到 PR，并记入账本：

```markdown
## 处置决定 · <票据> · <发现编号>
发现：<原报告链接与摘要>；复核：<补充报告链接与结论>
决定：<修复/接受风险/不适用>；决定人：<用户>
条件：<放行前必须满足的门禁，例如部署前的只读检查与期望结果>
```

带条件的决定，必须原样写进放行交接，作为部署前门禁（见 [放行与收尾](release.md)）。
