# 放行与收尾

放行把获审对象和剩余条件交给用户；合并、部署和真实验收由用户交给 `live-verify` 按授权执行。合并交给验收方，不交给该候选的作者或审查者。

## 放行前提

每个 PR 绑定最终候选身份，并且具备：

- PR 基线到最终候选的最终完整独立审查，以及修复期间各次增量复核的覆盖边界；
- 精确 head 的 `full-ci`，或项目对该变更等级要求的等价完整检查（如纯文档变更的文档检查），以及仍被触发的矩阵（见 [验证分层与测试矩阵](verification.md)）；
- 没有仍可能改变候选的任务；
- 所有处置决定的条件都已列为门禁。

集成 tree 与已审组合一致时，复用有效证据并补当前 CI；不一致时说明差异、验证影响，并取得覆盖当前候选的最终完整审查。候选或目标在交接后发生变化，先按 [账本](ledger.md) 对账并重新判断审查覆盖，旧交接不再适用。

放行后，按 [标签](labels.md) 把原 Issue 切到 `workflow.ready-for-acceptance` 对应的标签（默认 `awaiting-live`）。

## 放行交接字段

写入 `prompts/<票据或批次>-release-r<N>.md`：

```markdown
# <Issue/PR> · 放行交接 · 第<N>轮
原票与完成条件：<链接；待真实验收的行为>
目标与前置：<目标分支、依赖、基线>
获审候选：<完整 head/tree>；最终完整审查：<报告与 PR 评论链接>；CI：<检出对象、结果、链接>
合并：<方式（如 merge commit）>；可以直接运行的命令，并校验固定 head（如 `--match-head-commit <head>`）
关闭关键词：<已扫描 PR 正文和全部提交信息：结果；命中时说明会被关闭的票和处理方式>
部署前门禁：<处置决定的条件、命令、期望结果；不满足时停止并交回总控>
项目档案：<docs/agents/live-verify.md 或现有档案>
留痕：<每张原 Issue 都要留合并、部署和验收结果>
回报：<reports/ 中验收方本轮独有的路径>
```

多个同类 PR 一起验收时，再建一个批次索引：列出顺序、原 Issue、获审 head/tree、最终审查与 CI、前置与组合依据、待验收行为和未纳入项。批次清单只是索引，每个 PR 的审查记录和每张 Issue 的结果仍各自保留。

## 收尾

收到验收报告后：

1. 逐项对照现场核对报告：目标分支 head/tree 与获审 tree 一致、运行版本、门禁结果、每张 Issue 的留痕。
2. 每张原票：核对验收方切换的标签（`live-verified`、`changes-requested` 或 `blocked`）与结论一致；完成条件满足但还没关闭的，给出关闭命令；`changes-requested` 的票回到修复，`blocked` 的票记下解除条件。现场新发现的问题另开票，并回链旧票。
3. 遗留的低优先级发现，合成后续票；要记为已接受的，须由用户或项目授权的决策人明确接受，并按 [独立审查](review.md) 的处置决定发到 PR、记入账本。
4. 列出本范围创建的快照、工作树和分支；确认其中的工作已保全后，交用户回收。
5. 所有原票都已关闭或明确留给后续范围、没有未决门禁时，把范围状态写为 `complete`；仍有 `changes-requested` 或 `blocked` 的票时，保持当前阶段或写为 `blocked`，并写明解除条件。最后给出下一负责人。

需要用户执行的关闭、清理和回收，一律给出可以直接运行的命令。
