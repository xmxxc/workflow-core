# 实施交接

每轮为每个任务写一个新文件，`prompts/<票据>-<角色>-r<N>.md`；正在执行的文件保持不变。任务文件只写本轮变量，稳定规则交给本技能和项目文档。执行者按项目已安装的开发工作流自己选工作方法；专项工具（浏览器、外部抓取、专用实施入口）只在用户选定时写进任务。

## 任务文件字段

```markdown
# <票据> · <实施/修复/集成> · 第<N>轮

目标与完成标准：<本轮交付什么；怎样算完成>
来源：<仓库、Issue/规格、PR、待处理的审查评论>
起点：<候选身份 repo + PR + target + base + merge-base + head + tree，尚无 PR 时写目标分支与 base；前置是否满足>
工作位置：<分支/工作树；共享文件归属；需要保护的已有修改>
验证：<完成标准要求的证据等级，见 verification.md；缺陷修复附复现、回归和保留的失败探针>
授权：可以 <提交、推送自有分支、创建/更新 PR、Issue/PR 评论>；停在 <停止点>
开工：<先回读 Issue 最新状态，确认没有其他执行者；在 Issue 留接手记录：执行者标识、轮次、起点、本轮范围>
留痕：<PR 作者记录；PR 创建或更新后在 Issue 回链 PR；是否授权执行者切换标签>
回报：<reports/ 中本任务独有的绝对路径>，写明任务/会话标识、base/head/tree、提交、实际验证、留痕链接、剩余项
```

需要真实验收后才关闭的 Issue，PR 正文和提交信息都使用不会自动关闭它的关联方式，例如 `Refs #N`。集成任务另外写明：前置祖先、冲突归属、实际组合 tree 与已审 tree 是否一致。

执行者写自己的报告和 PR 记录；独立通过的结论由审查者给出，`state.md` 由总控维护。

## PR 作者记录

```markdown
## 作者<实施/修复/集成>记录 · 第<N>轮
范围：<起点> → <head>；tree：<tree>；目标：<分支>；来源：<Issue/审查评论>

| 问题/验收项 | 归属与严重度 | 本轮处理/提交 | 状态 |
| --- | --- | --- | --- |

验证：<实际检查、数量、跳过及原因、证据入口>
剩余：<前置、真实平台、未处理项>；下一步：待独立审查
```

用测试替身通过的部分单独列出，不据此宣称真实业务已完整通过。

## 完成

候选已固定，报告已保存，要求的留痕已由总控回读确认，并且已明确下一步是进入独立审查、继续修复，还是受阻。修复通常复用原 worker；新一轮任务文件写明当前真实起点和剩余问题。
