# 接收放行与合并

准备或执行合并时读取本文件；合并记录的格式见 [工作记录](work-records.md)。首次建立环境档案时，才另读 [项目档案](project-profile.md)。

## 接收放行

用户可能传来总控的放行交接、批次清单，或者只给一组 PR 号码。你自己从仓库和 tracker 回读每个 PR、原 Issue、审查与放行评论，以及可访问的总控账本，补齐以下信息：

- 目标分支、获审 head/tree；
- 最终完整独立审查和 CI 的实际检出对象；
- 前置依赖、剩余验收条件、本轮授权；
- 放行交接里的合并方式、合并命令、部署前门禁。

仓库和证据确实查不到时，才问用户缺什么。“测试通过”不等于已获独立放行。PR 已经合并时，核对实际合并记录并接着往下做，不重复执行。

默认先合并、再验收；事先约定为高风险的票，先完成前置验收。

## 合并前核对

- 回读当前 PR 和目标基线：head 与获审 head 一致；最终完整审查覆盖到当前候选；前置已满足；可以合并；必要 CI 的检出对象正确。
- 扫描关闭关键词，范围包括 PR 正文和全部提交信息（`close`/`fix`/`resolve` 加 `#N` 等）。会自动关闭需要真实验收的原票时，交回总控处理，或者在报告里写明合并后要重开哪些票。
- 按项目配置的方式合并（merge、squash、rebase），用平台支持的固定 head 条件防止合入新版本，例如 `--match-head-commit <获审 head>`。
- 候选变化、冲突、组合差异解释不清，或 CI 失败、原因不明时，交回总控。重跑后偶然通过，不能当作可以放行。

合并方式的平台规则不允许、或者自动化合并被拦截时，给用户一条可以直接执行的同一命令，并记录实际是谁执行的。

## 合并后

核对目标分支的实际提交、父提交和 tree，以及合并后的 CI。只有项目要求“与获审 tree 相同”时，才用 tree 比对作为条件；普通的并行合并，按实际组合判断。然后在每张原 Issue 发一条合并记录。

本阶段完成的条件：本轮要合并的 PR 都有实际结果和可核对的目标版本，或者明确了阻塞点和负责人；没合入的工作不进入验收清单。

## 批量合并

按用户交接的业务类型、目标分支和兼容环境组织一批，先列出 PR → 原 Issue → 验收行为的映射和依赖顺序。按依赖逐个过合并门槛并合并；叠加的 PR 逐层处理，复用有效证据，只补受影响的组合验证。组合证据不足的，先交总控补核，不在正式目标上冒险拼接。某一项受阻时，暂停它和依赖它的项，其余能独立交付的继续。

批量合并时，每张原 Issue 仍各发一条合并记录。用户的交互验收按完整业务流程组织：一次环境准备、一个健康基线，重复的操作合并起来做，但每张票各自给结论。
