# 合并与验收工作记录

这些记录由真实环境验收方维护。沿用项目的 tracker、标签映射和已有发布授权；权限不足时，把准确正文写进本轮报告并标“待发布”。发布前回读原票，同一轮已经发过的就复用链接；历史保留，不改旧评论。外部只放去敏证据，原始日志和私有标识按项目的访问边界保存。

批次报告先列：有序的 PR、原 Issue、实际合并版本与运行版本、每票的状态和标签。共享的健康基线或业务步骤只存一次证据，但在每张原 Issue 说明它覆盖了哪些行为，并给出该票自己的结论。

## 标签

实际字符串读取项目的 `docs/agents/issue-labels.md`；没有时，读 `triage-labels.md` 和 tracker 现有的标签，找语义相同的。下面是默认名。总控放行时，原票已经是 `awaiting-live`；合并之后、部署之前保持不变。

| 验收结果 | 原票标签 | 原票去向 |
| --- | --- | --- |
| 通过，包括“按契约的预期限制” | `awaiting-live` → `live-verified` | 完成条件满足后按授权关闭 |
| 通过，但发现与本票完成条件无关的新问题 | 原票 `live-verified`；新票从 `needs-triage` 开始 | 原票按授权关闭，新票回链原票 |
| 本票需求在真机上不成立 | `awaiting-live` → `changes-requested` | 保持打开，交回总控修复；重新放行后回到 `awaiting-live` |
| 环境或平台受阻，无法判定 | `awaiting-live` → `blocked` | 保持打开，写明解除条件；解除后回到 `awaiting-live` |

切换时同时移除残留的 triage 标签（如 `ready-for-agent`）。每个原票同时只有一个生命周期标签，每次切换都在报告里记“旧 → 新”。

## Issue：合并记录

每张原 Issue 在合并后发一条，批量合并也不省：

```markdown
## 合并记录 · <PR/时间>
执行：<会话标识；实际执行合并命令的人>；PR：<链接>
目标分支：<分支>；获审候选：<head/tree>
实际目标提交：<完整 SHA>；父/树：<值>；合并方式：<实际方式及固定 head 条件>
放行依据：<最终完整审查与 CI 的覆盖范围、链接、检出对象>
关闭关键词：<扫描范围与结果>
组合核对：<与获审对象或预期组合的关系、受影响的验证>
剩余：<部署、验收或其他切片>；标签：<当前值>
```

平台没有对应的 Git 对象时，使用可以核对的等价版本标识，并说明它的边界。CI 没跑完就写“待完成”，不提前写成功。父需求和多个目标分支，分别判断完成条件。

## Issue：真实环境验收

```markdown
## 真实环境验收 · <轮次>
执行：<会话标识>；环境与实际版本：<标识>；合并记录：<链接>
部署前门禁：<命令、对象、结果>
已通过：<用户可见的行为与证据>
预期限制：<按契约的限制及依据>
未执行/受阻：<原因、解除条件、是否影响本票完成>
偏差：<分类、现象、复现、去敏证据；根因已确认或待诊断>
后续票：<新开 issue 的链接>
完成条件：<逐项是否满足>；标签：<旧 → 新>；结论：<关闭/保持打开及理由>
回报入口：<本轮文件>；残留测试数据：<实际情况与处理方式>
```

无需真实验收的票：写明不适用的原因、已有的实际验证和完成条件，再按授权关闭。
